Mindustry Logic 单位控制指令深度详解

概述

本文档基于 Mindustry 159.7 版本源码，深入分析 logic 中所有与单位控制相关的指令：ubind、ucontrol、uradar、ulocate。每条指令从功能、参数类型、底层实现机制、边界条件等多角度进行严谨分析。

第一章：ubind（单位绑定）

1.1 指令格式

ubind type
  • 参数：type（可以是 content 类型的单位类型变量如 @mono，也可以是 unit 类型的具体单位实例变量）

1.2 功能说明

ubind 指令用于将处理器绑定到一个单位，绑定后该单位引用被存入环境变量 @unit。后续的 ucontrol、uradar、ulocate 指令都作用于 @unit 指向的单位。

1.3 源码实现分析

ubind 的实现位于 LExecutor.java 的 UnitBindI 内部类中。其核心逻辑分为三个分支：

分支一：当 type 是 UnitType（content 类型）时

if(type.obj() instanceof UnitType type && type.logicControllable){
    Seq<Unit> seq = exec.team.data().unitCache(type);
    if(seq != null && seq.any()){
        exec.binds[type.id] %= seq.size;
        if(exec.binds[type.id] < seq.size){
            exec.unit.setconst(seq.get(exec.binds[type.id]));
        }
        exec.binds[type.id] ++;
    }else{
        exec.unit.setconst(null);
    }
}

关键点：

  1. 处理器内部维护一个 binds 数组，以 UnitType.id 为索引，为每种单位类型维护一个独立的计数器
  2. 每次执行 ubind @mono 时，取 binds[mono.id] 对应的单位，然后计数器+1
  3. 计数器通过 %= seq.size 实现循环：到末尾后回到开头
  4. 单位列表来自 team.data().unitCache(type)，这是一个按单位类型分组的缓存
  5. 该缓存在 Teams.updateData() 中重建，遍历 Groups.unit 中所有单位按类型分组

分支二：当 type 是 Unit（unit 实例类型）时

else if(type.obj() instanceof Unit u && (u.team == exec.team || exec.privileged) && u.type.logicControllable){
    exec.unit.setconst(u);
}

关键点：

  1. 直接将 @unit 设置为指定的单位实例
  2. 不影响 binds 数组的计数器
  3. 需要单位与处理器同队（或处理器为特权世界处理器）
  4. 单位类型必须 logicControllable

分支三：其他情况

else{
    exec.unit.setconst(null);
}

@unit 被设为 null。

1.4 深度问答

Q1：ubind 能绑定什么单位？

ubind 可以绑定两种"单位"：

  • UnitType（content 类型）：如 @mono、@poly、@flare 等。这不是绑定某个具体单位，而是告诉处理器"给我这种类型的一个单位"。处理器会从队伍中该类型的单位缓存中循环取出单位。
  • Unit（unit 实例类型）：即一个具体的单位对象引用。这可以是之前保存到变量中的 @unit，也可以是 uradar 搜索到的目标，也可以是世界处理器 fetch 获取的单位。

不能绑定的单位：

  • 非 logicControllable 的单位（源码中检查 type.logicControllable）
  • 不同队伍的单位（非特权处理器）
Q2：ubind 能绑定玩家控制的单位吗？

可以，但有条件。玩家控制的单位仍然是 Unit 对象。如果用 content 类型绑定，且玩家控制的单位属于该类型且与处理器同队，它会被包含在 unitCache 中，因此可能被绑定。

但绑定后能否控制取决于 ucontrol 的 checkLogicAI 检查：

unit.controller().isLogicControllable()

玩家控制的单位的 controller 是 Player，其 isLogicControllable() 返回值决定了逻辑是否能接管控制。在实际游戏中，逻辑可以"绑定"玩家单位（获取其引用到 @unit），但控制行为可能受限。

Q3：如果只写两行指令——绑定单位并让单位移动到逻辑身上，为什么能绑定所有相关种类的单位？
ubind @mono
ucontrol move @thisx @thisy 0 0 0

这涉及单位绑定的循环机制：

  1. 处理器是循环执行的（执行到末尾回到开头）
  2. 每次执行 ubind @mono，binds[mono.id] 计数器+1，绑定下一个 mono
  3. 当计数器超过单位列表大小时，%= seq.size 使其回到0，重新从第一个 mono 开始
  4. 因此，只要处理器持续运行，它会依次绑定所有存活的 mono 类型单位，每个单位都会被执行一次 move 指令
  5. 这就是"群控"的基础：两行代码就能控制所有同类单位

重要：单位列表的大小和顺序在单位增减时会变化。当单位被删除时，使用"置换删除"（将末尾单位交换到被删位置），这会导致绑定顺序变化。

Q4：如果分别使用 ubind @mono 和 ubind @omura，绑定顺序还成立吗？
ubind @mono
ubind @omura

成立，但需要理解其独立性：

  1. binds 数组以 UnitType.id 为索引。@mono 和 @omura 是不同的 UnitType，有不同的 id
  2. ubind @mono 使用 binds[mono.id]，ubind @omura 使用 binds[omura.id]
  3. 两个计数器完全独立，互不影响
  4. 执行流程：第一次循环绑定 mono[0] 和 omura[0]，第二次循环绑定 mono[1] 和 omura[1]...
  5. 但注意：执行 ubind @omura 后，@unit 被设为 omura 单位，此时 ucontrol 作用于 omura。如果要在 ubind @mono 后立即控制 mono，需要在两条 ubind 之间插入 ucontrol
Q5：如果一个变量 U 存的是 unit 类型的变量，执行 ubind U 然后 ubind @omura，会发生什么？
ubind U
ubind @omura

分析：

  1. ubind U：U 是 unit 实例变量，走分支二。直接将 @unit 设为 U 指向的单位。不修改 binds 数组的任何计数器
  2. ubind @omura：@omura 是 UnitType，走分支一。使用 binds[omura.id] 取下一个 omura 单位
  3. 两条指令的绑定行为完全独立：U 的绑定不影响 @omura 的循环计数
  4. 最终 @unit 指向的是 omura 单位（第二条 ubind 覆盖了第一条的结果）
  5. 如果要在绑定 U 后控制 U，必须在两条 ubind 之间插入 ucontrol 指令

关键结论：

  • content 类型绑定使用独立的循环计数器（按类型）
  • unit 实例绑定是直接赋值，不参与循环
  • 每次执行 ubind 都会覆盖 @unit，之前的绑定结果丢失（除非保存到其他变量）

1.5 绑定顺序的底层机制

单位缓存 unitsByType 的构建过程（Teams.java）：

  1. 缓存通过 updateData() 方法定期重建
  2. 重建时遍历 Groups.unit（游戏中所有单位的集合）
  3. 按单位类型分组存入 unitsByType[type.id] 数组
  4. Groups.unit 的迭代顺序取决于单位的添加顺序（即单位的生成顺序）

因此，绑定顺序本质上是单位的生成顺序。同类型的单位按生成时间先后被依次绑定。

当单位死亡/被移除时：

  • 缓存会在下次 updateData() 重建时更新
  • Seq 的删除操作通常使用置换删除（swap and pop），即将最后一个元素移到被删位置
  • 这会导致绑定顺序在单位死亡后发生变化

第二章：ucontrol（单位控制）

2.1 指令格式

ucontrol type p1 p2 p3 p4 p5

2.2 执行前置条件

每次 ucontrol 执行时，首先调用 checkLogicAI() 验证：

  1. @unit 指向的对象必须是有效的 Unit（unit.isValid()）
  2. @unit 必须是当前绑定的单位（exec.unit.obj() == unit）
  3. 单位队伍必须与处理器相同（或处理器特权）
  4. 单位的 controller 必须是 logicControllable 的
  5. 如果 controller 不是 LogicAI，则创建新的 LogicAI 替换原控制器

验证通过后设置 ai.controlTimer = LogicAI.logicControlTimeout（10秒超时）。

如果10秒内没有新的 ucontrol/uradar/ulocate 指令作用于该单位，控制超时，单位恢复原AI。

2.3 逐指令深度分析

2.3.1 idle - 原地待命

ucontrol idle 0 0 0 0 0
  • 功能：设置 ai.control = idle，单位原地不动
  • 注意：idle 状态下单位仍会继续采矿和建造（这是默认行为），不是完全停止
  • 对比 stop：stop 会主动停止采矿和建造，idle 不会
  • 源码：ai.control = type; 仅此一行

2.3.2 stop - 停止一切

ucontrol stop 0 0 0 0 0
  • 功能：设置 ai.control = stop，同时 unit.mineTile = null 和 unit.clearBuilding()
  • 效果：单位完全停止移动、采矿和建造
ai.control = type;
ai.moveX = x1;
ai.moveY = y1;
if(type == LUnitControl.stop){
    unit.mineTile = null;
    unit.clearBuilding();
}
  • 注意：stop 仍然设置了 moveX/moveY，但在 updateMovement 中 stop 分支只调用 clearBuilding()，不移动

2.3.3 move - 移动到坐标

ucontrol move x y 0 0 0
  • 参数：x, y 为世界坐标（像素坐标，通过 World.unconv 转换）
  • 功能：设置 ai.control = move, ai.moveX = x, ai.moveY = y
  • 实现：LogicAI.updateMovement() 中调用 moveTo(Tmp.v1.set(moveX, moveY), 1f, 30f)
  • 注意：不会等待到达目的地就执行下一条指令。单位会持续向目标移动直到被新的控制指令改变

2.3.4 approach - 接近到一定半径

ucontrol approach x y radius 0 0
  • 参数：x, y 目标坐标；radius 接近半径
  • 功能：移动到距离目标 radius 范围内
  • 实现：moveTo(Tmp.v1.set(moveX, moveY), moveRad - 7f, 7, true, null)
  • 注意：实际停止距离比 radius 小7（源码中 moveRad - 7f）

2.3.5 pathfind - 寻路移动

ucontrol pathfind x y 0 0 0
  • 功能：使用寻路算法移动到目标坐标
  • 实现：飞行单位直接 moveTo；地面单位使用 controlPath.getPathPosition 寻路
  • 注意：地面单位会绕过障碍物

2.3.6 autoPathfind - 自动寻路

ucontrol autoPathfind 0 0 0 0 0
  • 功能：自动寻路至最近的敌方核心或敌人生成点
  • 实现：查找最近敌方核心，若距离超过 range*0.5 则移动。飞行单位直接飞向目标，地面单位使用 Pathfinder.fieldCore 寻路
  • 注意：在波次模式下，如果距离生成点足够近（dropZoneRadius + 120f），则不移动

2.3.7 boost - 助推

ucontrol boost enable 0 0 0 0
  • 参数：enable（0=关闭, 1=开启）
  • 功能：设置 ai.boost = bool(p1)
  • 实现：在 updateMovement 中，如果单位 canBoost 且非飞行单位：
    • shouldBoost = boost || unit.onSolid() || (飞行中且无法降落)
    • 调整 unit.elevation
  • 注意：只有 canBoost 的单位有效。飞行单位本身就在飞，boost 无额外效果

2.3.8 target - 瞄准坐标射击

ucontrol target x y shoot 0 0
  • 参数：x, y 目标坐标（世界坐标）；shoot（0=只瞄准不射击, 1=射击）
  • 功能：设置 ai.posTarget 为目标坐标，ai.aimControl = target，ai.shoot = shoot
  • 实现：在 target() 方法中返回 posTarget，单位武器瞄准该位置
  • 注意：只控制瞄准方向和是否射击，不控制移动

2.3.9 targetp - 瞄准目标射击

ucontrol targetp unit shoot 0 0
  • 参数：unit（Teamc 类型，可以是 Unit 或 Building 对象）；shoot（0/1）
  • 功能：设置 ai.mainTarget 为目标，ai.aimControl = targetp，ai.shoot = shoot
  • 实现：在 target() 方法中返回 mainTarget，单位武器自动瞄准该目标
  • 深度分析：p1.obj() 必须是 Teamc 接口的实例。Teamc 是 Unit 和 Building 共同实现的接口，因此 targetp 既可以瞄准单位也可以瞄准建筑
  • 注意：如果 p1 不是 Teamc（比如传了数字或 null），mainTarget 被设为 null，单位不会瞄准任何目标

2.3.10 itemDrop - 放下物品

ucontrol itemDrop building amount 0 0
  • 参数：building（Building 对象或 @air）；amount（数量）
  • 功能：将单位携带的物品放入指定建筑
  • 特殊：如果 building 是 @air（Blocks.air），则直接清空单位携带的物品（丢弃）
  • 距离检查：logicItemTransferRange + build.block.size * tilesize/2f（logicItemTransferRange = 5.625 tiles）
  • 超时：1.5秒传输延迟（transferDelay = 60f * 1.5f）
  • 条件：建筑必须同队、有效、allowDeposit()、单位在范围内、建筑接受该物品

2.3.11 itemTake - 取出物品

ucontrol itemTake building item amount 0
  • 参数：building（Building 对象）；item（Item content 类型，如 @copper）；amount（数量）
  • 功能：从指定建筑取出物品到单位
  • 距离检查：同 itemDrop
  • 超时：同 itemDrop
  • 条件：建筑必须同队、有效、有 items、item 是 Item 类型、单位在范围内、单位能接受该物品

2.3.12 payDrop - 释放载荷

ucontrol payDrop 0 0 0 0 0
  • 功能：释放单位携带的载荷（如建筑方块）
  • 条件：单位必须是 Payloadc 接口实例且有载荷
  • 超时：1.5秒

2.3.13 payTake - 拾取载荷

ucontrol payTake takeUnits 0 0 0 0
  • 参数：takeUnits（0=拾取建筑载荷, 1=拾取单位载荷）
  • 功能：
    • takeUnits=1：查找附近 AI 地面单位并拾取（距离 = unit.type.hitSize * 2f）
    • takeUnits=0：拾取当前位置建筑上的载荷
  • 超时：1.5秒

2.3.14 payEnter - 进入建筑

ucontrol payEnter 0 0 0 0 0
  • 功能：进入/降落到当前位置的建筑上
  • 条件：当前位置有建筑、建筑同队、build.canControlSelect(unit)
  • 用途：如 mono 进入修复厂、大型单位进入载荷工厂

2.3.15 mine - 采矿

ucontrol mine x y 0 0 0
  • 参数：x, y 采矿位置（世界坐标）
  • 功能：设置 unit.mineTile 为指定位置的 tile
  • 条件：unit.canMine() 且 tile 是有效矿脉
  • 注意：单位会自动飞/走到矿脉位置并采矿

2.3.16 flag - 设置标记

ucontrol flag value 0 0 0 0
  • 参数：value（数值）
  • 功能：设置 unit.flag = value
  • 特性：标记值永久保存在单位上，即使处理器被销毁也不会丢失。可通过 sensor 读取 @flag
  • 用途：给单位分组标记，如 flag=1 表示"采矿组"，flag=2 表示"战斗组"
  • 注意：每个单位只能存1个数字 flag

2.3.17 build - 建造建筑

ucontrol build x y block rotation config
  • 参数：
    • x, y：建造位置（世界坐标）
    • block：Block content 类型（如 @conveyor）
    • rotation：方向（0=右, 1=上, 2=左, 3=下）
    • config：配置值，可以是 Content（如 @copper 设置分类器）或 Building（复制另一个建筑的配置，如复制处理器代码）
  • 条件：需要 state.rules.logicUnitBuild 或特权处理器；unit.canBuild()；block 可建造
  • 实现：计算 tile 坐标，创建 BuildPlan，添加到单位的建造计划列表
  • 注意：如果目标位置已有相同建筑且旋转相同，则不重复建造

2.3.18 getBlock - 获取方块信息

ucontrol getBlock x y type building floor
  • 参数：x, y 坐标；type, building, floor 是输出变量
  • 输出：
    • type：该位置的 Block（建筑类型 content）
    • building：该位置的 Building 实例（如果有建筑）
    • floor：该位置的 Floor 或 overlay（如果有矿石覆盖层则返回矿石，否则返回地板）
  • 范围检查：max(unit.range(), unit.type.buildRange)
  • 注意：获取的 building 引用即使单位离开后仍可用于 write/draw（对 cell/bank/display），但不能用于 enable/disable 或 config

2.3.19 within - 距离检查

ucontrol within x y radius result
  • 参数：x, y 目标坐标；radius 半径；result 输出变量
  • 输出：result = 1（在范围内）或 0（不在范围内）
  • 注意：within 会触发控制状态（标记单位为被逻辑控制）。如果只需要距离检查而不想控制单位，应手动计算：op len dist dx dy 其中 dx=x1-x0, dy=y1-y0

2.3.20 unbind - 解除控制

ucontrol unbind 0 0 0 0 0
  • 功能：调用 unit.resetController()，单位恢复原 AI
  • 注意：解除的是"控制"状态，不是"绑定"。@unit 仍然指向该单位，但单位不再被逻辑控制

警告：除非确信已控制单位，否则不要随意使用 unbind，可能打断其他逻辑或单位默认AI

2.3.21 deconstruct - 拆除建筑

ucontrol deconstruct x y 0 0 0
  • 参数：x, y 拆除位置（世界坐标）
  • 条件：需要 state.rules.logicUnitDeconstruct 或特权处理器；unit.canBuild()
  • 实现：设置 ai.plan.breaking = true，添加拆除计划

第三章：uradar（单位雷达）

3.1 指令格式

uradar target1 target2 target3 sort 0 order output
  • 参数：3个筛选器、排序依据、占位符（填0）、排序方向（0=逆序/最远最低, 1=正序/最近最高）、输出变量

3.2 功能说明

以当前绑定的 @unit 为中心，在其范围内搜索单位，返回最符合条件的目标。是单位控制语句，会发出控制信号并标记单位为已控制。

3.3 筛选器

筛选器说明
any任意单位
enemy敌方单位
ally友方单位
player玩家控制的单位
attacker有攻击能力的单位
flying飞行单位
bossBOSS单位
ground地面单位

三个筛选器是 AND 关系：单位必须同时满足所有筛选条件才会被搜索到。

3.4 排序依据

排序依据说明order=1order=0
distance距离（取负值）最近最远
health当前血量最高最低
shield盾量最高最低
armor护甲最高最低
maxHealth血量上限最高最低

3.5 缓存机制

uradar 使用 LogicAI 的 radars 缓存：

  • ai.checkTargetTimer(this) 检查是否可以执行新搜索
  • radars 是一个 ObjectSet，存入的是指令对象本身
  • targetTimer 每 40 tick（约0.67秒）清空一次 radars
  • 在清空前，同一指令对象再次执行时返回 false，使用缓存结果
  • 这意味着同一单位短时间内重复 uradar 会返回旧目标

3.6 代码示例

# 搜索最近的敌方飞行单位
ubind @flare
uradar enemy flying any distance 0 1 target
jump skip equal target null 0
ucontrol targetp target 1 0 0 0
skip:

第四章：ulocate（单位定位）

4.1 指令格式

ulocate locate group enemy ore outX outY outFound outBuild
  • 参数：定位模式、建筑类型（仅building模式）、是否搜索敌方、矿物类型（仅ore模式）、输出X、输出Y、输出是否找到、输出建筑引用

4.2 定位模式

模式说明参数用途
building定位建筑group指定建筑类型，enemy指定敌我
ore定位矿脉ore指定矿物类型
spawn定位敌方出生点无额外参数
damaged定位受损建筑无额外参数（仅己方）

4.3 建筑类型（group参数）

core, storage, generator, turret, factory, repair, rally, battery, reactor

4.4 距离规则

  • 友方建筑：始终返回最近的（无距离限制）
  • 敌方建筑：仅在 max(27.5, unit.range()) 范围内返回
  • 矿物：返回最近的矿脉（可能不是最近的单个矿石tile，而是最近的矿脉）
  • 出生点：返回最近的敌方出生点
  • 受损建筑：返回最近的己方受损建筑

4.5 缓存机制

ulocate 也使用 LogicAI 的 execCache 和 checkTargetTimer：

  • 每个指令实例有自己的 Cache 对象（存储 x, y, found, build）
  • 在 checkTargetTimer 返回 false 时使用缓存值
  • 40 tick 内重复执行同一 ulocate 指令返回缓存结果

4.6 代码示例

# 定位最近的敌方核心
ubind @flare
ulocate building core true 0 coreX coreY found coreBuild
jump skip equal found 0 0
ucontrol move coreX coreY 0 0 0
skip:
# 定位最近的铜矿并采矿
ubind @mono
ulocate ore 0 0 @copper oreX oreY found 0
jump skip equal found 0 0
ucontrol mine oreX oreY 0 0 0
skip:

4.7 减少控制干扰

ulocate 是单位控制语句，会对单位发出控制信号。如果对非控制类逻辑（如只需定位信息的逻辑）反复使用 ulocate，会造成控制干扰。

解决方案：绑定一个未被控制的"侦察单位"，专门用于 ulocate，获取信息后通过 flag 或变量传递给其他逻辑。

第五章：综合实战示例

5.1 单控一个单位（稳定控制）

# 绑定一个空闲的 mono 并稳定控制
bind:
ubind @mono
# 检查是否已被其他逻辑控制
sensor ctrl @unit @controller
jump bind notEqual ctrl @this
# 检查是否已被其他逻辑控制（@controlled）
sensor controlled @unit @controlled
jump bind equal controlled @ctrlProcessor
# 现在有了一个未被控制的 mono
control:
ucontrol move 100 200 0 0 0
# 检查控制权是否还在
sensor ctrl @unit @controller
jump bind notEqual ctrl @this
jump control always 0 0

5.2 群控所有 flare 攻击敌方核心

ubind @flare
# 定位敌方核心
ulocate building core true 0 cx cy found 0
jump skip equal found 0 0
ucontrol move cx cy 0 0 0
ucontrol target cx cy 1 0 0
skip:

这个两行核心代码（ubind + ucontrol）在处理器循环执行时会依次控制所有 flare。

5.3 采矿自动化

loop:
ubind @mono
# 检查是否已有足够物品
sensor items @unit @totalItems
jump full greaterThanEq items 10
# 定位矿脉
ulocate ore 0 0 @copper oreX oreY found 0
jump loop equal found 0 0
# 去采矿
ucontrol mine oreX oreY 0 0 0
jump loop always 0 0
full:
# 去核心放矿
ulocate building core false 0 cx cy found core
jump loop equal found 0 0
ucontrol move cx cy 0 0 0
ucontrol itemDrop core 100 0 0 0
jump loop always 0 0

5.4 多类型单位协同

# 控制 mono 采矿
